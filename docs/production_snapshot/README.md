# What production holds that the repositories do not (read 24 Oct 2026)

`production_snapshot.json` is a read-only copy of facts about the shared Supabase project (`hwmynlghrmtoufyrcihp`): every column of the 16 tables the customer app reads, 44 row level security policies on them, and which status values are really in use. `customer_read_policies.sql` is the six "read your own rows" policies written out, for reading only. **Nothing was changed in production**: the facts came from `SELECT`s on `pg_policies`, `information_schema.columns` and `has_column_privilege`, run with the Supabase CLI (`db query --linked`). `supabase db pull` itself was not used: it needs Docker for a shadow database and this machine has none, and it would write a migration file into the website repository, which nobody had asked for.

`test/site/production_drift_test.dart` checks the app against this file, so it fails when the app reads a column or relies on a policy this snapshot does not have. The snapshot is a photograph: it does not notice a later change in production. Read it again (same queries, see the test's header) before relying on it after the website's next migration.

## What it showed

1. **Customers can read their own table bookings through the database, not only through a function.** Six policies, all of the form "signed in and `lower(customer_email) = lower(auth.email())`" (for the bottle lines, club payments, refunds and bottle substitutions: the same test on the parent booking): `site_orders`, `site_table_bookings`, `site_table_booking_bottles`, `site_table_booking_club_payments`, `site_table_booking_refunds`, `site_table_booking_bottle_substitutions`. The website's own account pages rely on exactly these.
2. **Three of those six are in no file of the website repository** (table bookings, booking bottles, bottle substitutions). Club payments and refunds exist only as test stand-ins in `tests/db/prod_shapes/`; orders is in migration `20260721`. A database rebuilt from the repository would show customers none of their table bookings. Recommended (not done): add the three as a website migration written `drop policy if exists` + `create policy`, which changes nothing in production.
3. **"Verified email" is not checked by the policies.** They compare the e-mail on the sign-in with the e-mail on the booking and never look at `email_confirmed_at`. Today that is harmless: of 84 accounts only 1 has an e-mail that was never confirmed, and it matches no booking or order (the other 6 accounts without a confirmed e-mail are phone sign-ups). It would matter if the project allows signing in before confirming: then someone could sign up with another person's address and read their bookings. Check Dashboard > Authentication > Providers > Email > "Confirm email" is ON (it cannot be read from SQL). This is the website's exposure too, not only the app's.
4. **Phone sign-ups see no bookings.** 6 accounts have no e-mail (phone sign-in), so `auth.email()` is empty and no booking matches. A customer who signed in with a phone number and bought with an e-mail address will see nothing in My bookings or My tickets. Needs a product decision (ask for an e-mail after a phone sign-in, or look bookings up by phone).
5. **Customers cannot read** `site_refund_requests`, `site_refund_policies`, `site_booking_seating` or `site_booking_moves` (no customer policy); those go through functions (`guest_request_refund`, `public_venue_refund_policy`).
6. `anon` has `SELECT` on every column of the booking tables, but no policy lets it see a row (the policies need `auth.role() = 'authenticated'` or a CMS admin). Safe as long as nobody adds a permissive policy.
7. **Statuses in use:** table bookings are `paid`, `pending` (abandoned or in-progress checkouts: 3 in 4 rows) and `cancelled`; `fulfillment_status` `confirmed` / `completed`; bottle lines `payment_status` `paid` / `due_at_venue` and `service_status` `awaiting_prep`, `preparing`, `ready`, `picked_up`, `served`. The checks in the code also allow `failed` and `refunded`.
8. **Columns that exist only in production** (and that the app reads) are all there: on `site_venues` `category, phone, website_url, hours_note, dress_code, capacity, music_genres, bottle_payment_mode, deposit_is_credit`; on `site_table_types` `table_view, privacy_level, seating_type, amenities, policy_note`; on `site_orders` `discount_cents`. The earlier "the website's types prove it" check can now rest on this.
